# 全功能最小示例项目：mini-gratitude（极简感恩日记 CLI）

**设计原则**：项目规模最小（< 300 行代码 + 文档），开发时间 < 4 小时（含所有工厂流程），但**必须覆盖工厂 100% 核心能力**。

**项目名**：`mini-gratitude`  
**领域**：productivity / personal  
**一句话描述**：一个命令行工具，让用户每天记录 1-3 条感恩的事，并支持简单查询和导出。

**为什么选这个**：
- 功能极简（add / list / export）
- 却能自然触发：需求访谈、架构决策（存储？隐私？）、TDD、任务图、ADR、Hooks、专家知识注入（可选“心理”专家）、安全审查、RETRO、MemoryStore 记录、甚至用 peer-review 对“导出格式”做多专家评审。
- 完整覆盖五阶段 + 所有 Gate + 所有主要 Agents/Skills/CLI 命令。

## 2026-06-23 当前适用说明

本示例仍用于演示 FORGE 五阶段项目孵化流程。当前工厂已额外具备 `_infra/network/` 联网增量能力：Search / Extract / PrivacyGateway / MCP Guard / Browser Automation / Local RAG / Ops。

因此使用本示例时：

- 五阶段流程仍按本文执行。
- 当前真实状态请以 `docs/PROJECT_STATE.md` 为准。
- 若需要演示联网能力，可在 BUILD/HARDEN 阶段额外调用 `_infra/network` 的安全搜索、隐私网关或 RAG 能力；不要把本文早期命令当作当前唯一入口。

## 项目目标（验收标准）
- 用户能 `gratitude add "今天和家人吃饭很开心"`
- `gratitude list` 按日期显示
- `gratitude export --format md > gratitude.md`
- 所有变更可追溯（R5 + ADR + CHANGELOG）
- 通过完整工厂五阶段 + Gate
- 复盘时产出至少 1 个可复用 Skill/Pattern

---

## 功能列表（MoSCoW）
**Must**：
- add（记录感恩）
- list（查看最近 N 条）
- export（导出为 markdown / json）

**Should**（在演示中实现以覆盖能力）：
- 简单数据持久化（SQLite 或 JSON）
- 基本隐私（本地 only）
- 使用工厂 peer-review 对“导出内容质量”做评审（演示多专家协作）

**Won't**（故意省略，保持最小）：
- Web UI、复杂统计、AI 自动生成感恩语

---

## 技术方案（高层次）
- CLI：Click 或 argparse（极简用标准库 argparse）
- 存储：本地 JSON 或 SQLite（选 SQLite 覆盖 MemoryStore 类似模式）
- 语言：Python
- 关键决策走 ADR（存储格式、隐私策略、是否用工厂 MemoryStore）
- 开发严格 TDD + pre-commit Hooks

### 步骤 1：DISCOVERY（需求探索）

**人工/Agent 操作**：
1. 复制 `docs/DISCOVERY.md` 模板并开始填写。
2. 加载技能：
   ```
   请作为 FORGE Factory 的 Orchestrator，严格加载 _factory/skills/discovery-interview.skill.md
   ```

**推荐提示词（给 Claude Code 或 Agent）**：
```
你是 FORGE Factory 主 Orchestrator。
项目：mini-gratitude（极简感恩日记 CLI）
当前阶段：DISCOVERY
请严格按照 _factory/skills/discovery-interview.skill.md 执行：
1. 向我（用户）进行结构化访谈，澄清动机、≥3 个具体场景、边界、MoSCoW、验收标准。
2. 主动指出至少 1 处空白或矛盾。
3. 调研同类（至少 3 个，包括 1 个失败案例）。
4. 最后产出完整的 docs/DISCOVERY.md。
每完成一个子任务就更新 docs/TASK_GRAPH.md（如果存在）或直接写 DISCOVERY。
所有新建文件必须加 R5 LLM 头部。
```

**预期输出**：
- `docs/DISCOVERY.md`（含用户场景、边界、验收标准）
- 至少 1 条“已指出空白”的记录
- 通过 **GATE-1**（人工确认：“这个需求边界我接受”）

**工厂能力覆盖**：discovery-interview skill、人工 Gate-1、R5 头、文档体系。

### 步骤 2：SPEC（架构 + 任务拆解）

**加载技能 + Agent**：
```
加载 _factory/skills/arch-design.skill.md
激活 arch-advisor Agent（_agents/arch-advisor.md）
```

**推荐提示词**（必须让 arch-advisor 写东西）：
```
你是 arch-advisor。
严格遵守 _agents/arch-advisor.md 权限：只能写 docs/SPEC.md、docs/adr/、docs/specs/、docs/RISK.md、docs/TASK_GRAPH.md。
项目当前在 SPEC 阶段。
输入：docs/DISCOVERY.md
请执行：
1. 提炼 3-5 个关键技术决策。
2. 为每个决策创建 ADR（使用标准模板，写到 docs/adr/ADR-001-xxx.md 等），必须解释 Alternatives、Rationale、Consequences。
3. 产出 docs/SPEC.md（技术栈、模块、数据流）。
4. 拆解为原子任务，生成 docs/TASK_GRAPH.md（用 ## Task: 格式，带 status、depends-on）。
5. 产出 docs/RISK.md。
所有文件必须有正确 R5 头部。
最后调用 forge check 验证。
```

**关键决策示例**（会出现在 ADR）：
- ADR-001：使用 JSON 文件 vs SQLite 做本地存储
- ADR-002：是否集成工厂 MemoryStore 记录运行数据（为了演示 compare-plans）
- ADR-003：隐私策略（local_only）

**预期输出**：
- 至少 3 个 ADR
- 完整的 TASK_GRAPH.md（5-8 个原子任务，有依赖）
- SPEC.md + RISK.md
- 通过 **GATE-2**（人工审批架构）

**此时运行**：
```bash
forge check
forge advance
```

**工厂能力覆盖**：arch-advisor + arch-design skill、ADR 系统（不可变）、TASK_GRAPH 解析/校验、R5、forge check/advance、GATE-2。

**典型任务拆解**（来自 TASK_GRAPH）：
