## 一、今天 429 现场数据（实测，非推测）

### 1.1 量级
- 今日（08-04）`/tmp/smart_proxy.err.log` 共 **324 次 429**。
- 两波爆发：
  - **04:38–04:58**（约 90 次）
  - **06:47–07:04**（约 234 次，最猛，14 分钟内几乎每秒被限流）
- `/stats` 实时 `retry_counters.429 = 315`（进程级累计）。

### 1.2 退避重试已生效但"重试也 429"
- 新代码：`可重试状态码 429` 424 次（退避 1.5s→3.0s→封顶 5s）。
- 旧代码残留：`不可重试状态码 429` 127 次（重启前历史）。
- **致命现象**：06:59–07:04 连续 30+ 个请求**全是 429，无一个 200 穿插**——限流窗口持续未过，重试只是把同样请求再打一遍，**越重试越 429，恶性循环**。

### 1.3 NIM 响应头实测（金标准，本机直连 integrate.api.nvidia.com）
- **429 响应**：仅 `date / content-type:application/problem+json / content-length:42 / vary`。
  - **无 `Retry-After`，无 `x-ratelimit-*`，无 `ratelimit-*`，无 `nvcf-*` 配额头。**
  - 响应体：`{"status":429,"title":"Too Many Requests"}`。
- **200 响应**：仅 `date / content-type / nvcf-reqid / nvcf-status:fulfilled / vary`。
  - **同样无任何配额/剩余额度头。**
- **并发实测**：20 并发 → **15×429 + 5×200**，推断免费档并发上限约 **5**。

### 1.4 关键结论
1. NIM 免费档**完全不暴露配额信息**（无 Retry-After、无 ratelimit 头），**只能本地主动预防 + 指数退避兜底**，无法依赖响应头自适应。
2. NIM 免费档约束是**并发（~5）+ RPM（待社区数据确认，常见说法 ~40）双重**，并发更紧。
3. 退避重试对"瞬时 429"有效，但对"持续限流窗口"**会加剧 429**（重试即新请求）。

## 二、根因链（今天 429 成灾）

1. **`FORGE_RPM_MAX=35` 来自项目根 `.env`（非 `_infra/.env`）**——这是真正的配置根因。
   - smart_proxy 的 `_load_dotenv`（第 44/46 行）会加载 `_infra/.env` **和** 项目根 `.env`；根 `.env` 末尾 `FORGE_RPM_MAX=35` 在 `RPMGuard` 实例化前注入 `os.environ`，覆盖代码默认 15。
   - 排查弯路：launchd plist/环境、`_infra/.env`、shell profile 均无此变量，一度误判为"进程加载旧代码"——实为根 `.env` 这个第二处 dotenv 源。
2. 35 RPM 远超 NIM 免费档承受力（实测并发 ~5、RPM 上限远低于 35）。
3. 飞书日常流量 + 子 agent + 排队重试，轻松突破 35 RPM。
4. NIM 疯狂返 429；退避重试把请求量推更高 → **429 风暴**（06:47–07:04 的 234 次）。
5. **RPMGuard 只防本地 RPM 超限，对 NIM 端 429 完全无感知**——429 后不降速、不熔断，继续放行新请求去撞墙。
6. **无并发上限**——NIM 对并发比对 RPM 更敏感，本地不限并发时极易触发 429。

### 已落地整治（2026-08-04 12:55 CST，进程 PID 6739 验证生效）
- 根 `.env`：`FORGE_RPM_MAX` 35→**15**；新增 `FORGE_REMOTE_MAX_CONCURRENCY=5`、`FORGE_CIRCUIT_BREAKER_TRIP=5`、`FORGE_CIRCUIT_BREAKER_COOLDOWN=45.0`、`FORGE_STREAM_REMOTE_RETRY_COUNT=2`。
- smart_proxy.py：新增 `CircuitBreaker`（连续 5×429 熔断、冷却 45s、half-open 探测）、`_remote_concurrency` 信号量（并发≤5）、`_backoff_with_jitter`（指数退避+全抖动，防惊群）、流式 producer 带 `exc_type` + consumer 对读类异常（ReadTimeout/ReadError 等）退避重试（修"空响应/turn 空挂 20 分钟"真凶）、`/stats` 暴露熔断与并发状态。
- 备份：`_infra/smart_proxy.py.bak.20260804_064307`、`.env.bak.20260804_125136`。
- 验证：单次请求 200 OK（TTFB 110s 为 NIM 端排队，非本地问题），未触发 429/熔断/重试。

### 附：另一独立缺陷（"空响应"真凶，非 429）
- 流式 producer 的 `except Exception` 把 `str(e)` 传出，httpx `ReadTimeout`/`ReadError` 的 `str(e)` 经常为空 → consumer `kind=="exception"` 分支**不重试、直接 0 token 结束 turn**。
- cc-connect 日志铁证：`turn_duration=20m1s output_tokens=0` 反复出现。
- 已在本轮修复（producer 带 `exc_type`，consumer 对读类异常退避重试）。

## 三、整治方案（分层，按优先级）

### P0 · 立即生效
1. **重启 smart_proxy 加载磁盘新代码**（`FORGE_RPM_MAX` 默认 15 + 429 退避 + 空异常重试）。
2. **`FORGE_RPM_MAX` 校准**：磁盘默认 15 偏保守但安全；待社区数据确认 NIM 真实 RPM 后再精调（见 P1）。

### P1 · 代码整治（本轮落地）
3. **429 风暴熔断（circuit breaker）**：连续 N 次 429 后进入"熔断态"，新请求强制排队等待冷却时间（如 30–60s），不再裸打上游。熔断态下 RPM 上限自动降到更保守值（如 5），冷却窗口无新 429 后恢复。
4. **RPMGuard 锁内不 sleep**：`acquire` 在锁内 `asyncio.sleep(60s)` 会阻塞所有请求。改为锁内只算窗口、锁外 sleep，或用信号量。
5. **并发上限**：NIM 实测并发 ~5。加 `FORGE_REMOTE_MAX_CONCURRENCY` 信号量（默认 5），从源头卡并发，比 RPM 更关键。
6. **退避加 jitter**：当前 1.5s/3.0s/5s 固定，多请求同步重试会"惊群"。改 `base * 2^attempt + random(0, base)`。

### P2 · 后续
7. **多 key 轮转**：`.env` 有 GLM/DeepSeek/QWEN/Pekpik 多个 key，429 时切换 key 分散限流。
8. **本地 fallback**：429 风暴时降级到本地模型（MTPLX/Ollama），保可用性。
9. **可观测**：`/stats` 暴露熔断状态、并发占用、最近 429 速率。
