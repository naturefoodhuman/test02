## 1. 工厂是什么？设计思想

FORGE Factory（AI 项目孵化工厂）**不是一个单体软件**，而是一套**可重复、可审计、可传承**的 AI 辅助项目孵化体系。

**核心理念**（来自 README + 架构设计）：
- 把“模糊想法”通过**结构化五阶段流程**变成“能跑的、可维护的 AI 软件”。
- 强调**人类在环（HITL）**：AI 只辅助，关键决策永远由人拍板。
- **可追溯**：所有决策、变更、知识都要留下痕迹（ADR、CHANGELOG、文件头 LLM 留痕 R5）。
- **工厂级知识复用**：_factory/ 里的 Skills、Patterns、Lessons、Experts 是跨项目共享的“可复用资产”。
- **单人可维护**：设计目标是在 M1 Max 64GB 单机上，一个人（或一个 Agent 团队）就能把项目从 0 做到可交付。
- **治理优先**：2026-06-16 后，所有变更必须遵循 Code → Tests → Documentation → CHANGELOG → ADR（重大决策）流程。

**不是**：不是一个“自动写代码的工具”。AI 负责执行结构化任务，人负责定义边界、拍板、审核。

**五阶段核心循环**（不可跳过）：
DISCOVERY（发现需求）→ SPEC（规格化 + 架构 + 任务拆解）→ BUILD（实现）→ HARDEN（加固/安全）→ RETRO（复盘提炼知识）

每个阶段都有**进入条件**、**退出产物**、**人工门控（HITL Gate）**。

## 2. 环境准备（从零开始）

### 2.1 硬件/软件要求
- macOS（推荐 M1/M2/M3/M4，64GB 内存最佳）
- Python 3.11+
- Ollama（本地模型）
- 可选：LiteLLM 网关 + 中国 API Key（GLM / DeepSeek / Qwen）

### 2.2 一步步安装（保姆级）

```bash
# 终端 A（长期开着）
ollama serve

# 终端 B（项目根目录）
cd /Users/naturist/MusicProject/AI-Project-Incubation-Factory

# 1. 克隆或进入项目（你已经在仓库里）
git pull origin main

# 2. 环境自检
bash _infra/setup.sh --check

# 3. 复制环境变量模板
cp _infra/.env.example _infra/.env
# 编辑 _infra/.env，填入 GLM_API_KEY（如果要用云端模型）

# 4. 安装 forge CLI（推荐）
cd _infra/forge_tools
pip install -e ".[dev]"   # 或 uv pip install -e ".[dev]"

# 5. 验证 forge
forge --help

# 6. （可选）启动 LiteLLM 网关（云端模型需要）
cd /Users/naturist/MusicProject/AI-Project-Incubation-Factory
source ~/.venv/bin/activate 
bash _infra/start-litellm.sh
```

**验证成功标志**：
- `ollama list` 能看到模型
- `forge status` 能运行
- `python -m pytest _infra/forge_tools/tests/ -q` 通过

完整真机验证见 `docs/REAL_MACHINE_VALIDATION.md` 和 `docs/SETUP_GUIDE.md`。

## 4. 核心概念：五阶段 + HITL Gate

### 五阶段定义（来自 phases.py + 手册）

| 阶段 | 进入条件 | 必须退出产物 | HITL Gate | 主要动作 |
|------|----------|--------------|-----------|----------|
| DISCOVERY | 无 | docs/DISCOVERY.md | GATE-1 | 访谈、澄清边界、场景、MoSCoW |
| SPEC | DISCOVERY.md | SPEC.md + TASK_GRAPH.md + RISK.md | GATE-2 | 架构、ADR、技术选型、任务拆解、风险 |
| BUILD | SPEC + TASK_GRAPH | BUILD_LOG.md | （无独立 Gate，靠 Hooks） | TDD 实现、测试、更新任务图 |
| HARDEN | SPEC | harden/SECURITY_REVIEW.md | GATE-4 | 安全审查、威胁建模、性能 |
| RETRO | 任意 | 写入 _factory/lessons/ | GATE-5 | 复盘、提炼 Skill/Pattern、知识入库 |

**HITL Gate 说明**（GATE_DESC）：
- GATE-1：需求边界由人定义
- GATE-2：架构与技术选型必须人工审批
- GATE-3：风险清单确认
- GATE-4：最终验收
- GATE-5：知识库更新必须人工审核（防污染）

**forge 命令辅助流转**：
```bash
forge status
forge check
forge tasks
forge advance
forge gate GATE-2
```

## 6. forge CLI 完整命令手册

在**项目根目录**（含 docs/）运行：

```bash
forge status                 # 扫描所有项目当前阶段
forge new <name> --domain <domain>   # 从 _TEMPLATE 创建新项目（自动加载匹配专家）
forge check                  # 校验 TASK_GRAPH + 当前阶段退出产物
forge tasks                  # 列出当前可执行（依赖满足）的任务
forge advance                # 检查能否进入下一阶段 + 需过哪个 Gate
forge gate GATE-2            # 打印 Gate 说明
forge retro generate         # 生成复盘草稿（可 --ai 辅助分析）
forge retro submit           # 提交到 _factory/lessons/（需 Gate-5）
forge eval --plans mtplx-hybrid   # A/B 测试模型方案（依赖 peer-review）
forge compare-plans --days 30     # 查看 MemoryStore 方案对比报告
```

**内部机制**：
- 阶段检测基于 `_detect_phase` + 退出产物存在性。
- TASK_GRAPH 使用自定义 Markdown 解析器（零依赖）。

## 7. 标准工作流（端到端）

1. **启动环境**（Ollama + 可选 LiteLLM）
2. **进入项目目录**
3. **forge status** 了解当前阶段
4. **按阶段加载对应 Skill + Agent**
5. **执行任务** → 更新 TASK_GRAPH status → 跑测试（Hooks 自动）
6. **forge check / advance** 验证可前进
7. **通过 HITL Gate**（人工确认）
8. **进入下一阶段**
9. **RETRO** 时必须产出至少 1 个可复用资产，并通过 Gate-5 入库

**每步必须记录**：BUILD_LOG.md、CHANGELOG.md、文件头 R5 留痕。

## 9. 如何让工厂接手已有项目

1. 把项目复制/移动到 `projects/xxx/`
2. 确保有 `docs/` 目录
3. 手动补齐或让 Agent 补齐 AGENTS.md + .claude/（参考 _TEMPLATE）
4. `forge status` 让它自动探测当前阶段
5. 从当前阶段继续走流程（补 DISCOVERY/SPEC 等）
6. 强烈建议补全治理文件（ADR、CHANGELOG、R5 头）

- 永远先读 HANDOFF + 最新 GOVERNANCE_CHECK + 对应 ADR。

## 12. 常见错误与排查

- “找不到模块”：`export PYTHONPATH` 或用 `pip install -e`
- 阶段检测不对：检查 docs/ 里退出产物是否存在
- TASK_GRAPH 循环依赖：用 `forge check` 看报错
- Gate 被绕过：必须人工输入确认
- 模型调用失败：检查 Ollama/LiteLLM 是否启动 + 隐私策略
  - 特别：`ModuleNotFoundError: No module named 'websockets'` → 必须 `uv pip install 'litellm[proxy]'`（不是只装 litellm）
- 知识污染：Gate-5 必须人工审

详见 HANDOFF.md “常见排障” + 各阶段 Skill 的“反模式”。
